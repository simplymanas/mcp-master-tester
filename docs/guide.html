How to test an MCP server

Connect to the server, call its tools by hand, then check the tool definitions with lint and the tools themselves with a smoke test, in the browser or in CI.

Quick start

npx mcp-master-tester

Open http://127.0.0.1:6280 and click Connect. The default fields launch the official reference server (npx -y @modelcontextprotocol/server-everything), which uses every feature, so you can try everything before pointing it at your own server.

It needs Node.js 20 or later. To use a different port, set PORT, for example PORT=7000 npx mcp-master-tester. If the port is taken, it says so and exits.

Or run it from source:

git clone https://github.com/simplymanas/mcp-master-tester.git
cd mcp-master-tester
npm install
npm start

Connecting to a server

Server typeSettings
Local npm packagestdio → Command npx, Arguments -y @modelcontextprotocol/server-filesystem /path/to/dir
Local scriptstdio → Command python, Arguments my_server.py, Working dir as needed
Needs an API keystdio → + var → GITHUB_PERSONAL_ACCESS_TOKEN = … (hidden automatically)
Remote (current spec)Streamable HTTP → URL https://host/mcp, plus a Bearer token if required
Remote (legacy)SSE → URL https://host/sse

The connection panel shows Not connected, Connecting… or Connected, and once connected, the server's name and version, the transport and the process id. Edit any field and click Reconnect to apply it. Closing or reloading the tab ends the session and stops the server process.

Keys and auth. Environment variables named like *KEY*, *TOKEN*, *SECRET* or *PASSWORD* are hidden as you type. If a remote server answers 401, the app asks for a token and retries. If a stdio server crashes and its error output mentions a missing key, the app offers to add it and reconnect.

Profiles are saved in your browser. Secrets are never stored, so the app asks for them when you connect.

Running tools by hand

Each tool's inputSchema becomes a form: text and number fields, checkboxes, drop-downs for enums (including oneOf with titles), multi-select arrays and JSON editors for objects. Required fields are checked before anything is sent, and Edit as JSON lets you type the arguments directly. Ctrl/⌘ + Enter runs the selected tool.

  • Results: text (JSON is pretty-printed), images, audio, resource links, embedded resources and structuredContent. A tool's isError result is shown separately from a protocol error, with how long the call took.
  • While it runs: set a timeout per call and watch progress from notifications/progress. Tools marked destructive ask for confirmation, and each tool keeps a call history.
  • Resources and prompts: read static resources, fill in URI templates, and see the messages a prompt returns.
  • Elicitation: when a server sends elicitation/create, a form built from its requestedSchema appears.
  • Protocol log: every JSON-RPC frame in both directions with request-to-response time, the server's stderr, and notifications/message entries, with a logging/setLevel control when the server supports logging.

Lint

Lint reads the server's tool list and checks each definition against the MCP spec and against what models handle well. A model only knows a tool through its name, description and schema, and that whole list is sent with every request, so a vague or bloated definition costs accuracy and context on every call.

In the app, open the Lint tab. The tab count shows errors and warnings, coloured by the worst one, then info findings in muted text: 2 · 14 means 2 errors or warnings and 14 info suggestions.

What it checks

  • Spec: inputSchema and outputSchema must be of type object, required fields must be defined, and names must be valid and unique.
  • Look-alike tools: names so close a model may pick the wrong one (get_user and getUsers), and near-identical descriptions. A prefix every tool shares, or a description template most of them share, doesn't count.
  • Descriptions: missing, very short, never saying when not to use the tool, or so long they eat context. It also flags a whole tool list that is too big.
  • Parameters: missing types or descriptions; no required list when a parameter has no default; free-form strings that list fixed values (should be an enum); strings that should be booleans, numbers, dates, URLs or emails; and values with no example.
  • Naming: names that aren't snake_case, and names that break the server's own convention.
  • Annotations: missing read-only and destructive hints, and tools marked read-only whose name says they change something (cancel_booking) or that are also marked destructive.
  • Output size: list and search tools with no limit or pagination parameter.
  • From real calls in the app: a result over about 10,000 tokens, and an isError result with no useful message for the model to recover from.

From the command line

The same rules run in a terminal or CI. The command connects, lists the tools, prints the findings and exits non-zero when there are any at your chosen level.

# stdio: put the server command after --
npx mcp-master-tester lint -- node dist/index.js

# Streamable HTTP (add --sse for the legacy SSE transport)
npx mcp-master-tester lint --url https://example.com/mcp --header "Authorization: Bearer $TOKEN"
OptionWhat it does
--fail-on <level>Exit 1 at error (default), warn or info findings, or never
--format <format>text (default), json, or github for GitHub Actions annotations
--show-infoList info findings too (they're always counted)
--env KEY=VALUE, --cwd <dir>Environment and working directory for a stdio server
--url <url>, --sse, --header "Name: value"Connect to a remote server
--timeout <ms>Give up after this long (default 30000)

Exit codes: 0 passed, 1 findings at or above --fail-on, 2 the server couldn't be started or reached, or the options were wrong. If a stdio server crashes on start, its stderr is printed.

Smoke test

Lint asks whether the tool definitions are good. The smoke test asks whether the tools actually work: it calls each read-only tool once and fails if one doesn't answer properly. It runs in the app's Smoke tab and from the command line:

npx mcp-master-tester smoke -- node dist/index.js
mcp-master-tester smoke · my-server v1.4.0 · 6 tools · stdio

  pass  ping_db           2 ms
  pass  get_weather      48 ms
  warn  find_user         3 ms  returned an error for the made-up "id": No user with id "test". Ids look like "u_1".
  fail  get_report       12 ms  result breaks its outputSchema: … data/celsius must be number
  fail  slow_query    30001 ms  no answer: timed out after 30001 ms
  skip  delete_user             not marked read-only

✖ failed: 2 failed, 1 warning, 2 passed, 1 skipped. Failing on: fail.

What runs, and how far to trust it

readOnlyHint is the server describing itself. If a tool is mislabelled, the smoke test calls a tool that writes. Choose by what is at stake.

The serverUseWhat runs
Holds real data, or isn't yours--tool a --tool bExactly the tools you name. An allow-list is the only mode that doesn't rely on the server's own labels.
A local or test instanceno flagTools marked readOnlyHint: true, except those whose name or other annotations contradict it: named like a write (cancel_booking), or marked destructive as well.
A throwaway instance--allEvery tool.

The name check only catches careless labels. A get_quote that also fires a webhook looks read-only to any tool, which is why the allow-list comes first. If no tool runs at all, the command fails, because a run that called nothing has proved nothing.

What is sent

A value for each required parameter and nothing else:

  1. the schema's default, first examples entry, const or first enum value, if it has one;
  2. otherwise a made-up placeholder: "test", 1, or a value that fits the format (a URL, an email address, a date).

In the app, your last run of a tool in the session comes first. To turn warnings into real checks in CI, print what would be sent, replace the made-up values, and pass the file back:

npx mcp-master-tester smoke --print-args -- node dist/index.js > smoke.json
# edit smoke.json, for example:  { "find_user": { "id": "u_1" } }
npx mcp-master-tester smoke --args smoke.json -- node dist/index.js

How answers are judged

ResultWhen
passThe tool answered with a normal result.
failNo answer before the timeout; the server closed the connection; a protocol error (the tool threw instead of returning an error result); a result that breaks the tool's outputSchema; or an error result for arguments that came from the schema or from you.
warnAn error result, or "invalid params", for made-up arguments: the tool answered, but a placeholder can't prove it works. Also a result over about 10,000 tokens.
skipNot clearly read-only, left out with --skip, or listed after a tool that crashed the server.

Expected skips

A pass covers only the tools that ran. When tools are skipped because they aren't marked read-only, the run says which ones. To make that a failure, use --fail-on skip, and list the tools you expect to go untested with --skip:

npx mcp-master-tester smoke --fail-on skip --skip add_card --skip delete_card -- node dist/index.js

The tools you name show as "skipped on request" and don't count against the run. A new tool that nobody marked read-only fails it, and so does a renamed one, because a --skip name the server doesn't have is an error. --fail-on skip is the strictest level, so warnings fail the run too; clear them by giving real arguments, as above.

Options

OptionWhat it does
--allAlso run tools that aren't clearly read-only. They may change data.
--tool <name>Run only this tool (repeatable), read-only or not. The safest way to choose what runs.
--skip <name>Leave this tool out (repeatable). With --fail-on skip, this is how you list the skips you expect.
--args <file>JSON file of arguments: { "tool_name": { "param": "value" } }
--print-argsPrint the arguments that would be sent, and run nothing
--fail-on <level>Exit 1 on fail (default), also on warn, also on skip, or never
--timeout <ms>How long each tool may take (default 30000)

--format, --env, --cwd, --url, --sse and --header work as they do for lint, and so do the exit codes. A misspelt tool name in --tool, --skip or the --args file is an error (exit 2), so a renamed tool can't quietly drop out of the test.

GitHub Actions

Build your server, then run lint and the smoke test against it. With --format github, each finding shows as an annotation on the workflow run. Add --tool for each tool if the server in CI holds anything you care about.

- run: npm ci && npm run build
- run: npx -y mcp-master-tester lint --format github --fail-on warn -- node dist/index.js
- run: npx -y mcp-master-tester smoke --format github --args smoke.json -- node dist/index.js

Security

  • The backend listens on 127.0.0.1 only, because it can run any command you enter in the stdio form. Don't expose it on a network.
  • Requests with a Host other than 127.0.0.1 or localhost, or an Origin other than the app itself, are rejected. That blocks DNS-rebinding attacks and other websites open in your browser.
  • Everything a server sends (names, descriptions, schemas, results, logs) is treated as untrusted and escaped before display. A Content-Security-Policy backs that up.
  • Secrets stay in memory in the browser tab and the backend process. Profiles save names only, never values.
  • Tools only run when you click Run, and tools marked destructive ask first. The smoke test is the exception, which is why it only runs tools marked read-only, or the ones you name.

To report a security issue, see SECURITY.md.

Limitations

  • No browser sign-in (OAuth) for remote servers. Use a Bearer token or custom headers instead.
  • Sampling (sampling/createMessage) and roots are not advertised to servers.
  • URL-mode elicitation is not advertised, so servers can only ask for input with a form.

These are on the roadmap, and several are marked as good first contributions.
