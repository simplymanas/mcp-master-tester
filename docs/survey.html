Survey · 21 November 2026

How much context do popular MCP servers use?

I listed the tools of 28 popular MCP servers and measured what each one sends to the model on every request, before you've asked anything. Most are small. Four send over 10,000 tokens.

  • 28servers, 335 tools
  • 4over 10,000 tokens
  • ~1,900tokens for the median server
  • 7servers with no safety labels

Why the size of a tool list matters

When an MCP client connects to a server, it fetches the server's tool list: each tool's name, description and input schema. Unless the client loads tools on demand, it sends that whole list to the model with every request, so the model can pick a tool.

That text is paid for on every turn, and it takes room the conversation could use. It adds up across servers: connect the four largest below and about 77,000 tokens go out before you type anything.

Four servers send over 10,000 tokens

Each of the four is large for a different reason:

  • Firecrawl (~24,600): 28 tools with detailed input schemas. firecrawl_search alone is about 2,600.
  • Azure (~19,800): 74 tools, the most in the survey. Descriptions make up 44% of it.
  • Notion (~19,000): its tools are generated from Notion's API spec, and 98% of the size is input schemas.
  • Desktop Commander (~13,400): descriptions are 76% of it, and eight of them are over 500 tokens each. About a quarter of all its characters are indentation inside the description text.

Big isn't automatically wrong. A detailed description can help a model use a tool correctly. The question for each server is whether every request needs all of it.

Seven servers have no safety labels

Tool annotations tell a client what a tool does to the world: readOnlyHint marks a tool that only reads, and destructiveHint one that can delete or overwrite. Clients use them to run safe tools without asking and to warn before risky ones.

306 of the 335 tools have them. Of the 29 that don't, 28 are on seven servers that label none of their tools: AWS Documentation, Tavily, Browserbase, GitMCP, DeepWiki, MarkItDown and Astro Docs. Six of the seven only search or read, which makes it an easy fix: one line per tool.

One parameter in four has no description

274 of 1,170 parameters have no description of their own, so the model has only the name to go on. They are concentrated in five servers:

  • Firecrawl: 118 of 171
  • Desktop Commander: all 72. It explains parameters inside each tool's description instead, which is part of why those are long.
  • Notion: 31 of 71
  • Git: 21 of 32, and Filesystem: 18 of 25. Both are official reference servers that many people copy.

Output schemas are still rare

An outputSchema tells the client what shape a tool's result will have, so the result can be checked and used without guessing. 70 of 335 tools declare one, on 12 servers. Eight servers declare one for every tool, among them Firecrawl for all 28 of its tools.

The good news

  • No spec errors: every input schema is an object, every tool name is valid and unique, and every required parameter is defined.
  • Every one of the 335 tools has a description.
  • Tool names that a model could mix up are rare. A handful remain, such as firecrawl_monitor_run and firecrawl_monitor_check.

For server authors: five fixes

  1. Label every tool. Add readOnlyHint: true to tools that only read, and destructiveHint: true to ones that delete or overwrite.
  2. Describe each parameter in its schema, not only in the tool description. A sentence on what it is and an example value is enough.
  3. Keep tool descriptions to what the model needs to choose the tool. Remove indentation from multi-line description strings: it's sent too.
  4. Watch the total. If the tool list is past about 10,000 tokens, consider fewer, broader tools, or a setting that loads only the groups a user needs.
  5. Declare an outputSchema for tools that return structured data.

To check your own server, run lint against it. It warns when the tool list passes about 10,000 tokens or a description passes about 500, and lists missing labels and parameter descriptions as suggestions:

npx mcp-master-tester lint --show-info -- node dist/index.js

Method

  • When: 21 November 2026. Each package was the latest release on npm or PyPI, run with npx or uvx and default settings. Playwright and Chrome DevTools ran with --headless --isolated; Filesystem and Git were pointed at an empty test folder and repository.
  • Remote servers were reached over Streamable HTTP without signing in.
  • Only tool lists were read. No tool was called on any vendor's server. The tool lists were checked with MCP Master Tester 1.4.2's lint.
  • Tokens are estimated as the characters of each tool definition, as compact JSON, divided by four. That is the estimate lint uses. Real tokenizers differ by model, and runs of spaces usually cost less than this suggests, so read the figures as approximate and compare servers with each other. Clients also wrap tool lists in their own format, which adds a little.
  • Settings change the numbers. Several servers can expose fewer tools through their options. These figures are for the defaults.
  • Not included: Supabase, Sentry, Stripe and Brave Search need an API key just to list their tools, and Semgrep's remote server refused the connection.

I make MCP Master Tester, the tool used for these checks. If a number here is wrong, or a server has changed since, please open an issue and I'll correct it.
